# Хедер и футер — единый источник правды

Хедер и футер сайта больше не редактируются отдельно в каждом
HTML-файле. Источник — два файла в `partials/`:

- `partials/header.html`
- `partials/footer.html`

## Как внести изменение

1. Правишь `partials/header.html` или `partials/footer.html`.
2. Запускаешь:
   ```
   node build.js
   ```
   (или `npm run build`, если используется npm)
3. Скрипт сам находит блок между `<!-- HEADER:START -->` /
   `<!-- HEADER:END -->` (аналогично для FOOTER) на каждой странице
   из списка `PAGES` внутри `build.js` и заменяет его актуальным
   содержимым партиала. Сами страницы остаются обычным статичным
   HTML — никакого JS-инклюда в браузере, никакого билд-сервера,
   просто перезаписанные файлы.
4. Коммитишь и `.html`, и изменённый партиал.

Скрипт идемпотентен — можно гонять `node build.js` сколько угодно
раз, дублей не появится.

## Почему так, а не JS-инклюд (fetch + innerHTML)

JS-инклюд означал бы, что хедер/футер физически отсутствуют в HTML
до выполнения скрипта в браузере — хуже для SEO и даёт заметное
мерцание при загрузке. Build-скрипт собирает готовый HTML заранее,
результат ничем не отличается от ручного копирования, кроме того,
что копирование теперь делает скрипт, а не человек.

## Активный пункт меню

Раньше `class="active"` на нужном пункте `<nav>` был захардкожен
вручную в каждой копии хедера — отсюда расхождения между страницами.
Теперь это не нужно: `js/nav-active.js` сам подсвечивает пункт меню,
чьё `data-page` совпадает с `<body data-page="...">` текущей
страницы. Значения уже расставлены: `home`, `team`, `catalog`,
`blog`, `contact`.

Если добавляется новая страница в меню — присвой ей свой
`data-page` на `<body>` и на соответствующем пункте `<nav>` в
`partials/header.html`, ничего больше делать не нужно.

## Перенос в WordPress

`partials/header.html` и `partials/footer.html` — это будущие
`header.php` и `footer.php` темы. Перенос:

1. Контент копируется как есть (теги `<header>`/`<footer>` остаются
   снаружи `get_header()`/`get_footer()`, как в любой стандартной
   теме).
2. `href="index.html"` и подобные внутренние ссылки на статичные
   файлы заменяются на `<?php echo home_url('/'); ?>` /
   `esc_url(home_url('/team/'))` и т.п.
3. Меню (`<nav class="header-nav">`) можно либо оставить статичным
   списком ссылок, либо подключить к `wp_nav_menu()` для
   редактирования из админки — структура с `data-page` для
   подсветки активного пункта при этом не понадобится: WordPress
   сам умеет помечать текущий пункт класс `current-menu-item`.
4. `js/nav-active.js` в этом случае становится не нужен — можно
   удалить, его работу возьмёт на себя WP Walker для меню.
5. Футер: пункты "Услуги"/контакты можно оставить статичными или
   вынести в ACF Options Page, если контент-менеджеру нужно менять
   их без правки кода.

## Известный существующий баг (не связан с этой унификацией)

Ссылка "Политика конфиденциальности" в футере
(`href="index.html#privacy"`) никуда не ведёт на любой странице —
секция на `index.html` называется `id="page-privacy"`, а не
`id="privacy"`, и скрыта классом `.page` без `.active`, так что
переход по этому якорю ничего не показывает. Это было так и до
унификации хедера/футера (на 7 из 8 страниц), сейчас просто стало
одинаково сломано везде, а не на 7 страницах из 8. Чинить отдельной
задачей — либо сделать `index.html#page-privacy` рабочим якорем с
небольшим JS, который активирует секцию по hash при загрузке, либо
(разумнее, особенно учитывая планы на WordPress) сделать полноценную
отдельную страницу `privacy.html`.
